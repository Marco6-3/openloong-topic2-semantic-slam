# 技术路线

## 总体原则

先保证几何地图和轨迹完整，再增加语义。初赛公开数据说明未列出相机，因此在审计原始 bag 前，不把 RGB 语义 SLAM 设为初赛依赖。

```text
传感器输入
  ├─ 初赛：MID360 + IMU + RTK
  └─ 复赛：VLP-16 + RGB + 仿真状态
          ↓
传感器适配层
          ↓
LiDAR-IMU里程计 → 全局约束/回环 → 稠密几何地图
          ↓                         ↓
逐帧语义推理 → 多帧关联/投票 → 静态语义地图
          ↓
动态目标层与过滤
          ↓
PCD、轨迹YAML、语义说明、RViz与性能日志
```

## 建图基线

优先评估 FAST-LIO2，原因是其面向高效 LiDAR–IMU 里程计，并提供 Livox 数据路径和 PCD 累积保存能力。官方仓库：<https://github.com/hku-mars/FAST_LIO>。

是否适用必须由 bag 审计决定：

- 若 `/livox/lidar` 含可靠的每点时间戳，可直接适配；
- 若为普通 PointCloud2，需要核实字段中是否仍有 `time`/`timestamp`；
- 若完全缺失点时间戳，必须记录运动畸变风险，并评估转换或替代方案；
- 若外参已知，优先固定外参，不让在线外参估计引入不稳定性。

LIO-SAM 作为全局图优化、GPS和回环方案的参考实现，不默认作为MID360第一基线。官方仓库：<https://github.com/TixiaoShan/LIO-SAM>。

## RTK融合

建议先离线建立稳定基线，再逐步加入全局约束：

1. WGS84 经纬高转换到局部 ENU；
2. 选择首个高质量 RTK 固定解作为局部原点；
3. 用 `status` 和 `position_covariance` 过滤或加权；
4. 估计 LiDAR轨迹与RTK轨迹之间的刚体变换；
5. 分别比较仅LIO、LIO+RTK位置、LIO+RTK位置+航向；
6. 在回环或轨迹图优化后重新生成全局地图，避免只改轨迹而不更新点云位置。

建议至少记录：起终点误差、对RTK的水平误差统计、回环区域重影和处理耗时。

## 语义地图

### 初赛无RGB时

采用 LiDAR-only 3D分割或检测：

1. 点云预处理和体素化；
2. 逐帧语义推理；
3. 使用估计位姿投影到全局坐标；
4. 对同一体素进行标签概率累计；
5. 低置信结果标记为 `unknown`；
6. 人和车辆等动态类别进入动态层，不直接固化到静态地图。

可评估 MMDetection3D 中的3D语义分割实现：<https://github.com/open-mmlab/mmdetection3d>。预训练模型与比赛场景可能存在域差异，必须通过可视化和小规模人工抽查验证。

在官方未指定类别前，可以仅用于内部实验的候选类别包括：地面/道路、建筑/墙、植被、车辆、行人、杆状结构、其他、未知。最终类别必须以组委会答复为准。

### 复赛有RGB时

使用 RGB 检测/分割、相机内参与 LiDAR–相机外参，把图像语义投影到点云；复用初赛的多帧关联、静态地图和动态层接口。

## 输出建议

最终格式尚待组委会确认。在内部开发阶段先同时保留：

- `map_geometry.pcd`：纯几何地图；
- `map_semantic.pcd`：带标签或颜色字段的语义地图；
- `semantic_labels.yaml`：标签ID、名称、颜色和说明；
- `path.yaml`：与官方样例一致的完整轨迹；
- `metrics.json`：内部验证指标，不一定提交；
- `final_parameters.yaml`：最终可复现参数。

## 不应过早做的事

- 在未审计bag前锁死ROS消息适配方案；
- 在组委会未答复前把自定类别当作官方类别；
- 只凭进程成功退出判断地图正确；
- 只修正轨迹而继续提交未经重建的旧点云；
- 把大数据、权重、PCD或视频提交进Git历史。
